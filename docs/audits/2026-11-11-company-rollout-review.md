# 公司全员开放前审查

审查日期：2026-11-11。对象：当前工作区后端、积分与用量记录、网页/MCP 共用服务及测试启动配置。

> 后续修复记录（同日）：用户指定的四项已在代码中修复并通过隔离回归：三个遗漏入口的零余额拦截、真实音频时长计费、异常模型输出的供应商用量记录、服务端固定任务集合的搜索批次。网页和 MCP 请求流程同步更新。额外修复了 multipart 上传完成后用户上下文丢失的问题，确保文件访问和积分归属正确。失败模型输出记录供应商 token，但不扣用户积分。以下正文保留审查当时的证据，不代表其他上线风险已经修复。共享运行服务未在本次代码修复中重启。

## 结论

**暂不建议直接向全公司开放。** 主力云端功能已接入积分记录，但存在余额校验遗漏、时长计费失真、供应商用量漏记等已复现问题；当前共享测试实例也不能直接当正式公司服务。

本次只审查，未修改业务代码、依赖和运行配置，未重启服务、改动线上用户数据或调用付费生成。以下“已复现”均使用隔离测试、模拟供应商或临时音频样本，不代表真实供应商账单已经发生相同金额的损失。

## 一、哪些功能没有完整进入积分系统

| 功能 | 当前情况 | 需要处理 |
| --- | --- | --- |
| ElevenLabs 配音、音效、音乐、跨语种配音 | 已有积分与供应商用量记录 | 保留现有规则，补齐边界验证 |
| 语音转文字、变声、人声分离 | 已记分，但按文件大小推算时长 | 改用服务端实测时长，统一预留与结算 |
| 文本翻译、分析、提示词、歌词、OCR、需求拆解、命名等 GPT 功能 | 正常成功路径已有 token 与积分记录 | 补齐余额预留、异常输出的供应商成本记录 |
| 指定语言翻译、两种视频声音设计分析入口 | 成功后记分，但漏接余额拦截 | 上线前修复，不能允许零余额继续调用 |
| 单次/批量联网音效搜索、时间线搜索 | 已有按批收费机制 | 维持每批 1 分；由服务端确定批次范围，防止无限复用 |
| 本地音乐分轨（含多轨分离） | 当前挂载没有传入积分预留回调 | 明确免费还是收费，并增加资源用量统计 |
| 本地 Seed-VC、音色克隆及批量克隆 | 未进入当前积分账本 | 明确政策，限制重任务占用 |
| 音频转 MIDI | 未进入当前积分账本 | 明确政策，增加资源用量统计 |
| 上传、音效库管理、下载、普通剪辑/格式转换/混音 | 不产生云模型调用时未扣模型积分 | 可以继续免费，但仍需权限、文件和资源限制 |

注意：旧 `pointsBilling.ts` 的另一套本地功能费率没有挂载为当前计费规则，不能以其中有常量就判断已经接入。当前 `/api/points/me` 已退役。当前执行规则应以公司积分账本及实际挂载路径为准。

本地处理没有云 API 费用，是否收费是内部制度选择，不应直接套用 ElevenLabs 价格。即使免费，也应记录谁使用、运行时长、任务量及失败情况。

## 二、上线前必须处理

### 1. 付费入口漏校验余额【已复现】

`server.ts:883` 使用 Express 挂载路径列表控制余额，但 `/api/ai/translate` 不会覆盖带连字符后缀的 `/api/ai/translate-language`；声音设计路径也存在相同问题。

受影响的付费入口：

- `/api/ai/translate-language`（`server.ts:4716`）。
- `/api/ai/audio-design-video-preuploaded`（`server.ts:4501`）。
- `/api/ai/audio-design-video`（`server.ts:4551`）。

隔离服务测试：余额为 0 时普通翻译返回 429，但指定语言翻译返回 200，累计使用变为 5001.5/5000 分。后两项已通过代码确认调用付费分析，未逐项进行同样的服务复现。

这属于“记账但允许透支”，不是完全没有记录。纯本地关键帧提取和预上传准备不应误判为模型扣费遗漏。

建议：统一付费能力入口，由后端显式执行预算预留，避免依赖易漏项的路径前缀列表。

### 2. 同一段音频会因格式不同扣不同积分【已复现】

`src/services/elevenLabsService.ts:157` 用文件字节数和假定码率估算时长，语音转文字、变声、人声分离将这个值用于实际积分结算。

按当前语音转文字 0.6 分/秒的规则，实长 60 秒应约 36 分；隔离样本结果：

| 实际音频 | 算法估计 | 当前扣分结果 |
| --- | --- | --- |
| 60 秒、16kHz、单声道、16bit WAV | 约 20 秒 | 约 12 分 |
| 60 秒、48kHz、双声道、16bit WAV | 约 120 秒 | 约 72 分 |

视频先提取为低采样率音频再识别也会受到影响。建议先用受限媒体探测取得真实时长，再按相同数值做预留与结算；不需要更换模型或提高费率。

### 3. 模型预留金额不足，无法严格控制额度【已复现】

多种文本/视觉请求只预留 0.1 分，但 GPT 最低结算通常为 1 分，音频分析最低为 10 分。隔离测试中，剩余 0.5 分仍可完成翻译，累计使用达到 5000.5/5000 分。长任务、多轮助手与并发请求会扩大该风险。

另外，部分预留在 HTTP 连接关闭时释放，但供应商工作不一定同步中止；这是代码层面确认的生命周期风险，尚未模拟真实供应商断连场景。

建议：按模型最大输出和任务规模设合理预留，限制单任务预算；后台任务、断线和重试共用稳定任务 ID，最终结算前保留预留，确保只结算一次。

### 4. 模型输出异常时，供应商 token 可能漏记【已复现】

`src/services/aiGateway.ts:95、125、193` 在记录用量前检查 incomplete、空内容和 JSON 格式。模拟返回中包含明确 usage 的成功 HTTP 响应，分别触发未完成输出、无效 JSON、空文本后，平台新增用量记录均为 0。

建议先保存供应商实际用量，再校验业务内容。供应商成本账和用户积分账应区分：失败任务是否退还用户积分可以按制度决定，但已消耗的供应商 token 必须可追踪。

### 5. 上传与请求解析依赖有已知安全更新【扫描确认】

本次 `npm audit --omit=dev` 报告 9 个受影响包：7 个高危、2 个中危，无 critical；均有可用修复。当前安装 `multer 2.2.0`、`body-parser 1.20.5`。优先处理运行时上传/请求解析依赖，再核对构建工具依赖在正式环境中的可达性，不能把全部扫描结果都等同于可远程利用。

官方公告说明特定 multipart 或压缩请求体可导致进程退出；本次未发送攻击载荷或使运行服务崩溃。部分登录解析发生在业务登录校验之前，需纳入升级验证。

- [Multer 官方安全公告](https://github.com/expressjs/multer/security/advisories/GHSA-wc9g-mqfw-jrwm)
- [body-parser 官方安全公告](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828)

应升级到能消除当前全部相关公告的版本，不能只按某一历史公告的最低修复版本升级。升级后复测上传、登录、压缩请求解析和 MCP 文件流程。

### 6. 共享测试服务不能直接作为正式公司服务【配置确认】

`scripts/start-test-server.mjs:69` 明确使用测试模式、关闭飞书登录并配置共享测试账号，通过局域网 HTTP 访问。这不能保证每位同事拥有独立身份及积分归属。

正式开放需使用生产模式、HTTPS、每人飞书登录，并在飞书管理后台确认应用可见范围。代码读取 OAuth 用户身份，但没有额外确认公司租户和在职状态；应用本身的企业可见范围是否已经足够限制访问，仍需管理员核实，不能直接认定外部人员一定能登录。

MCP token 默认 30 天、最多 90 天，目前验证不联查在职状态，也缺少管理员集中停用账号并撤销其全部 token 的流程。建议补上离职/禁用机制，避免停用飞书之后旧 token 仍可用。

## 三、开放前建议同时加固

### 批次收费边界

`src/services/sfxBatchServer.ts:236` 允许客户端提交 `searchBatchId`。同一用户在去重周期内复用相同 ID，可以让不同关键词的新搜索继续免扣；隔离测试已确认首次收费、第二次不同搜索不收费。批量模块去重可达 24 小时，时间线模块默认 30 分钟。

维持“单次/批量每批 1 分”政策即可。应由服务端创建批次并固定任务集合、数量、有效期和结束状态；用户再次发起新的一批就是新批次。

### 全公司费用上限

已有个人额度不等于公司现金预算保护。ElevenLabs 账号余额主要用于显示，未见覆盖全部供应商的公司日/月费用硬上限。建议增加总预算告警和硬停止额度，同时保留个人额度与项目池审批，避免大量账号或异常重试集中消耗。

### 并发和服务器资源

现有通用写请求限制为每人 4、全局 16；这是请求数，不代表可以同时使用的总人数。后台任务返回 202 后不再占用该 HTTP 计数，各模块队列也不等于统一的供应商/GPU 限流。

本地分轨已有单工作者、队列上限 32、每人最多 2 个未完成任务，不能笼统说没有保护。但其他重处理需要统一排队；100MB 内存上传、120MB JSON 上限叠加并发时，仍可能产生较大内存压力。普通音频 decode 路径也缺少部分其他 FFmpeg 路径已有的超时保护。

正式服务器上线前应按真实音频时长、视频大小和同时操作场景做负载测试，测 CPU/GPU、内存、磁盘和等待时间。本次未对共享服务做压力测试，不能据此承诺支持多少人。

### 账本、存储与备份

- 目前用 JSON/JSONL 文件与进程内状态管理账本、额度、会话及预留；README 已明确只支持单 Node 进程。公司服务器可以先单进程运行，但不能直接开 PM2 cluster/多实例扩容。多实例前需共享数据库及事务化扣分。
- 用量账本同步追加、查询时全量同步读取；规模扩大后会阻塞请求处理。
- `usageTracking.ts:27` 捕获记录失败后只警告，磁盘满/写入失败时可能“调用成功但账本没有落盘”。应增加持久化失败告警及可恢复的用量补记机制。
- 当前每用户 1GB 检查发生在请求开始前，没有对本次新文件做原子空间预留，并发生成可能越过上限。
- 私有上传目录默认有 7 天清理；长期项目引用不必然阻止源文件被清理。共享音效库使用另外的存储位置，不应混同。正式上线应明确临时文件、项目素材、音效库的不同保存周期。
- 本次未验证外部备份及恢复能力。上线前应演练恢复用户/额度配置、用量账本和需要长期保存的音效文件。

### 文件处理边界与素材来源

MCP 的部分 FFmpeg 路径已经使用协议/格式白名单，普通解码路径尚不一致。隔离样本中，伪装成 mp4 的 concat 清单能让普通解码读取同目录的另一份测试音频，白名单路径会拒绝。尚未证明跨用户文件读取或外网请求；建议统一限制格式、协议、时长及运行超时。

联网音效可继续按既定要求直接使用，并保留来源记录；技术上可下载、可试听不代表已经取得对外商用授权。公司正式对外发布素材时仍需确认来源许可。本次未新增授权拦截或改变搜索流程。

## 四、已有的有效保护

已检查的代码和测试中，普通用户身份由服务端确定，伪造前端身份不能改变扣分归属；MCP token 使用哈希存储并有过期/撤销机制，工具及路由有白名单，私人文件下载有归属校验。

MCP 上传到个人工作区与上传到共享音效库属于不同权限：前者是登录用户工作流的一部分，后者要求管理权限。普通用户不能因此获得共享音效库管理权限。

OAuth state 绑定发起登录的浏览器、单次使用；退出会撤销会话。外部素材抓取已有 HTTPS、DNS/IP 校验、重定向复核和下载大小限制。这些保护有效，但不足以抵消前述积分与上线配置问题。

## 五、验证结果与边界

- 安全、MCP、生产音效流程、错误脱敏、飞书认证、联网搜索相关及后台分析任务测试：76/76 通过。
- `npm run lint`（类型检查）：通过。
- `npm run test:points`：6 项单元测试通过；积分集成测试有一处旧断言失败。`tests/companyPoints.test.ts:98` 仍期待 500，而先前错误处理修改后实际返回 422。仅在测试加载时临时修正该断言，集成测试其余流程通过；源文件没有修改，不能把原始命令报告成全部通过。
- 额外隔离验证：零余额遗漏入口、0.1 分预留透支、真实音频格式导致的时长误算、异常模型输出漏用量、客户端批次 ID 复用。
- 未进行真实付费调用、生产环境负载测试、飞书后台配置检查或外部备份恢复演练。本报告是代码与测试审查，不能视为全面渗透测试或供应商账单对账结果。

## 六、建议修复顺序

1. 补齐所有付费入口余额校验，统一预算预留与任务结算生命周期。
2. 修正媒体实测时长与供应商异常用量记录；补齐回归测试。
3. 升级运行时安全依赖并复测；修正旧测试断言，取得原始测试命令通过的结果。
4. 固定服务端搜索批次边界，明确本地功能免费/收费政策和重任务队列。
5. 配置正式 HTTPS、逐人飞书身份、企业访问范围及账号/MCP 停用机制。
6. 增加公司总预算、监控告警、备份恢复；在正式服务器完成小范围试运行与负载测试，再扩大开放。

现有普通 5000 分/月、专业 20000 分/月及部门 15% 项目池政策无需因本次审查直接调整。应先修复计量与额度控制，再用真实使用数据评估额度是否合适。
